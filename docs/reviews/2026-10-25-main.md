## Summary
The slice adds a useful, role-gated brand library, but the current implementation is not ready to mark complete. The live worker route crashes on a stale Prisma delegate, the schema change has no deployable migration, and blob cleanup can delete a still-referenced file before an update succeeds. Upload transport, source validation, filters, and several user-facing controls also need correction.

## Blockers

### 🔴 New delegate is absent from the cached Prisma client, `lib/brand-assets.ts:114`
**Problem**: The new query unconditionally calls `prisma.brandAsset.findMany`, while the cached-client compatibility check in `lib/prisma.ts:29` stops at `scheduleEvent`. A preexisting dev singleton is consequently reused after generation even though it has no `brandAsset` delegate. The parent verifier reproduced `/worker/brand-assets` failing with `Cannot read properties of undefined (reading 'findMany')` at this call.
**Why it matters**: The feature currently cannot load in the running application; a passing build and mocked query test do not establish working routes.
**Suggested fix**: Extend schema compatibility handling for BrandAsset, regenerate the client, restart/reload as required, and verify both authenticated routes against the real database.

### 🔴 The database change is not represented by a migration, `prisma/schema.prisma:627`
**Problem**: The enum and model are added only to the schema; the diff and untracked file list contain no migration. The implementation used `prisma db push`, and the parent reports migrate status as up to date with the existing 16 migrations, none containing BrandAsset.
**Why it matters**: A database built or upgraded through the repository's migration history will lack the enum/table and the new routes/actions will fail. Local push is not a deployable schema change.
**Suggested fix**: Add and validate the SQL migration, preserving the already-pushed local data, and verify the migration history creates the new schema on a clean database.

### 🔴 Cleanup deletes data before the database operation succeeds, `app/actions/brand-assets.ts:223`
**Problem**: Update deletes the existing blob at line 231 before validating the associated project at line 241 and before persisting at line 254. Delete similarly removes storage at line 327 before deleting the row at line 333. A missing project or database failure leaves an unchanged row pointing at a deleted file.
**Why it matters**: An unsuccessful edit or delete can permanently destroy the existing asset despite returning an error.
**Suggested fix**: Complete validation and the database mutation first, then perform narrowly scoped, retryable cleanup of the superseded file. Cover failed project validation and failed DB mutation with assertions that the old blob remains intact.

## Major

### 🟠 The advertised upload limit cannot pass the configured transport, `app/actions/brand-assets.ts:65`
**Problem**: The action accepts and the UI advertises 25MB, but `next.config.ts` limits Server Action request bodies to 2MB. Bundled Next documentation confirms this applies to the entire multipart body before the action runs. Additionally, `components/brand-assets/brand-asset-dialog.tsx:224` has no catch/finally around the action call, so framework/network rejection leaves `isUploading` true and Save disabled.
**Why it matters**: Ordinary brand PDFs/ZIPs between 2MB and 25MB fail before the supposedly protective validation, and the editor becomes stuck.
**Suggested fix**: Choose a supported upload transport/limit consistently with deployment constraints, validate it in the client, and always release pending state with an actionable error. Test a file above 2MB through the real HTTP path.

### 🟠 Upload storage access contradicts the existing configured integration, `app/actions/brand-assets.ts:98`
**Problem**: This feature uses `BLOB_READ_WRITE_TOKEN` with `access: "public"`; the existing working avatar integration in `app/actions/profile.ts:54` uses the same token with `access: "private"`. No separate public store is configured, and cards consume returned URLs directly without an authorized download/preview handler.
**Why it matters**: A private store cannot satisfy the public upload path, and merely switching the write to private would leave previews/downloads inaccessible. Actual store behavior still requires the parent's live upload verification; the code-level inconsistency is definite.
**Suggested fix**: Reuse the established private-storage architecture with authenticated asset delivery, or explicitly configure a separate public store only if public access is intended and approved. Verify upload, preview, and download together.

### 🟠 Arbitrary supplied file URLs become deletion authority, `app/actions/brand-assets.ts:324`
**Problem**: Create/update accept any `fileUrl` string, and cleanup decides ownership using only `.includes("vercel-storage.com")`. There is no binding between an uploaded file, its brand-asset path, and the persisted record; the dialog also discards the returned pathname. A manager can save a URL of another file in the same store, such as an avatar or another asset, and subsequently trigger its deletion through this feature.
**Why it matters**: Brand-asset editing can destroy unrelated stored content. A hostname substring is neither store ownership nor file ownership validation.
**Suggested fix**: Persist server-verified upload identity/path, restrict managed files to the owned brand-assets namespace/store, and ensure cleanup cannot remove shared/referenced or unrelated files. Reject forged URL/path pairs and test that unrelated blob URLs never reach `del`.

### 🟠 A malformed external link can crash the entire library, `lib/validation/brand-assets.ts:5`
**Problem**: `HTTP_URL_REGEX` checks only a protocol prefix. For example `https://[` passes it, but the card unconditionally executes `new URL(asset.externalUrl).hostname` in `components/brand-assets/brand-asset-workspace.tsx:440`, which throws for that value.
**Why it matters**: A single accepted bad link prevents all users from rendering the listing containing the record.
**Suggested fix**: Parse and validate HTTP(S) URLs server-side rather than matching their prefix, and render malformed historical values defensively. Add a regression for invalid URLs that previously passed the regex.

### 🟠 Updates can remove every usable asset source, `app/actions/brand-assets.ts:214`
**Problem**: Only create enforces the file/link/palette invariant. Update accepts all three as null without merging against the stored source fields; its existing-record select does not even retrieve externalUrl or colorPalette. The editor can switch an existing asset to an empty source and save it.
**Why it matters**: Persisted assets can become unusable while appearing successfully saved, violating AC-4. Standalone clientId updates also skip create's CLIENT-role validation.
**Suggested fix**: Validate the merged final asset, including its effective source and client association, before mutation. Test partial updates, explicit source clearing, and non-client IDs.

### 🟠 Scope and client/project selections use incompatible query predicates, `lib/brand-assets.ts:71`
**Problem**: The asset query uses project/client IDs instead of the selected scope through an else-if chain. The category-count query at line 129 builds different predicates and overwrites the selected client under CLIENT scope or the selected project under PROJECT scope. For example CLIENT plus one client lists that client's assets but counts every client's assets.
**Why it matters**: Filter selections and counts disagree, and General Studio plus a client can show client assets despite the chosen scope.
**Suggested fix**: Define compatible filter semantics and build one shared base predicate for listing, total, and category counts; vary only the explicitly intended category filter. Cover combinations rather than just each filter alone.

### 🟠 Required project filter has no UI, `components/brand-assets/brand-asset-workspace.tsx:300`
**Problem**: The toolbar exposes scope and client only. Project options are passed to the component, but are used solely by the editor; there is no projectId selector or current project display.
**Why it matters**: AC-5 explicitly promises filtering the library by project. Workers cannot narrow a large project-specific library to the project they need through the interface.
**Suggested fix**: Add the project filter with readable labels, URL state, and coherent client/scope interaction, and verify it for both roles.

### 🟠 Selects repeat the raw-value and width regressions, `components/brand-assets/brand-asset-dialog.tsx:392`
**Problem**: Category/client/project selects omit both a label mapping (`items` or explicit SelectValue contents) and full-width trigger classes. The installed Base UI SelectValue resolves labels from items and otherwise falls back to the raw value; option JSX alone does not supply that mapping. Toolbar scope/client selects at workspace lines 301/317 have the same label problem.
**Why it matters**: Users see enum values and database IDs in selected controls; the dialog triggers inherit the shared `w-fit` width instead of filling their columns. This reproduces the usability failures already reported elsewhere in the app.
**Suggested fix**: Supply readable selected labels for all values and sentinels, make dialog controls fill responsive columns, and test selected values plus long names on mobile and desktop.

### 🟠 Most of a larger palette is inaccessible to workers, `components/brand-assets/brand-asset-workspace.tsx:407`
**Problem**: Validation allows 20 swatches, but the preview renders only the first 8 and detail buttons only the first 5. There is no read-only detail/expand view; workers cannot open the manager editor.
**Why it matters**: A valid palette containing 9–20 colors silently hides later colors from the users who need to inspect and copy them, despite displaying the full color count.
**Suggested fix**: Expose every swatch and its name through an accessible expanded/detail presentation or full list, preserving the compact card. Verify worker copying of the final swatch in a 20-color palette.

## Minor

### 🟡 Cleared and abandoned uploads are orphaned, `app/actions/brand-assets.ts:225`
**Problem**: Cleanup requires a truthy replacement URL, so switching a file asset to a link/palette never cleans its former blob. Immediate uploads are also never reclaimed when the dialog is cancelled or a second file replaces an unsaved first upload.
**Why it matters**: Routine editing accumulates unmanaged storage that no record can clean up later.
**Suggested fix**: Include explicit file removal in post-save cleanup, and track temporary uploads with a bounded cleanup lifecycle.

### 🟡 Clipboard success is reported before success is known, `components/brand-assets/brand-asset-workspace.tsx:157`
**Problem**: `navigator.clipboard.writeText` is neither awaited nor caught, but the success message appears immediately. Permission rejection or an unavailable Clipboard API gives false confirmation or an exception.
**Why it matters**: The advertised one-click copy feature can tell users a value is copied when it is not.
**Suggested fix**: Await the write, show success only after completion, and show a helpful failure state/manual copy fallback.

### 🟡 Documented hashtag search does not match stored tags, `components/brand-assets/brand-asset-workspace.tsx:284`
**Problem**: The placeholder encourages `#tag`, but the query compares the complete lowercased string with tags stored as `tag`. Clicking a tag or navigating back also changes URL search without synchronizing the search input initialized at line 120.
**Why it matters**: A supported-looking search can produce no result and the visible query can disagree with the results.
**Suggested fix**: Normalize the optional hashtag prefix and keep the input aligned with URL navigation and tag clicks.

### 🟡 Scope completion claims exceed the evidence, `docs/scope/scope.md:209`
**Problem**: Migration and live verification are checked complete although the migration is absent and the running route fails. The feature section says done while the overview table says in-progress; the spec is also labeled complete.
**Why it matters**: The next agent or release decision cannot rely on this status as an accurate readiness signal.
**Suggested fix**: Reconcile status and verification evidence after the reported failures are fixed and verified. Preserve an explicit distinction between implemented code, automated checks, and successful live behavior.
